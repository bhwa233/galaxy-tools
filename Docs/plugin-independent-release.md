# 宿主与插件独立发布

2026-11-07 与用户确认的方案。目标：宿主（启动器）和每个官方插件各自构建、各自发布，只有对应部分有修改时才触发对应的构建，互不牵连。

## 1. 现状

- 推一个 `v*` 标签后，`build-artifacts.yml` 一次性编译所有插件的原生组件，从源码构建所有官方插件，打进安装包并发布 GitHub Release。插件有修改也只能跟着宿主一起发版。
- 客户端已能按插件检查更新：内置插件的更新源默认是 `registry.npmjs.org` 的 `latest` 通道（`scripts/build-official-plugins.mjs`）。只有 registry 上的版本比已安装的高，才会提示用户更新（`desktop-host.ts`）。但官方插件都是 `"private": true`，从未发布过，所以这条路径一直没用上。
- 内置插件只在首次安装时装进去。已安装的插件，只有在内置包版本更高、且旧包无法在新宿主上运行时，才会被自动替换。所以插件内容改了却没升版本号，老用户就拿不到这次改动。v0.1.6 就遇到了这个问题。
- 原生组件已有单独的 `native-payloads-*` 标签发布，但所有插件的原生组件打在一个包里。
- 插件通过清单里的 `api` 范围声明兼容的宿主 API 版本。
- npm 上还没有 `@spark233` scope，仓库 Actions 也没有配置任何 secret。

## 2. 已确认的决定

1. 插件发布到 npm 公共 registry。
2. 发布由版本号变化触发：main 上某个包的 `package.json` 版本号与已发布的版本不同，就构建并发布这个包。不为每个插件单独打标签。
3. 便签不再与宿主绑定，改为和其他插件一样独立发布。便签数据放进插件自己的数据区。当前是 MVP 阶段，不迁移旧数据，也不兼容旧数据。
4. 原生组件放进各插件自己的发布流程。
5. 分阶段实施：先拆不需要改架构的插件；再把翻译、OCR、截图的界面代码移进各自的包；最后拆便签。

## 3. 发布线

| 发布线          | 构建输入                                                          | 产物                                             | 触发                                                                             |
| --------------- | ----------------------------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------- |
| 宿主            | `apps/desktop`、`packages/sdk`、`packages/ui`，以及尚未独立的插件 | NSIS 安装包、`latest.yml`，发布到 GitHub Release | main 上 `apps/desktop/package.json` 版本号变化时，自动打 `v<version>` 标签并发布 |
| 每个独立插件    | `packages/official/<name>`，含它自己的原生组件                    | npm 包 `@spark233/plugin-<name>`                 | main 上这个插件的版本号变化时                                                    |
| SDK、UI（可选） | `packages/sdk`、`packages/ui`                                     | npm 包，供第三方插件开发使用                     | 版本号变化时                                                                     |

宿主安装包里的内置插件改为由一份锁定清单决定，清单记录每个插件的名称、版本和完整性校验值。已独立的插件按清单从 npm 下载已发布的包，再打进安装包；尚未独立的插件仍从源码构建。这样内置的插件和线上发布的是同一个包，宿主构建也不再需要编译这些插件的原生组件。

## 4. 防止“内容改了、版本没升”

为每个插件记录一份构建输入的指纹：插件目录，加上它在构建时引用的宿主源码和共享包文件。CI 检查到指纹变了但版本号没变时直接失败，提示升版本号。这能同时覆盖第 6 节所说的隐藏依赖：宿主里被插件引用的界面代码改了，相关插件会被要求升版本号。

PR 检查按影响范围执行：typecheck 和测试只跑受影响的包（按 pnpm 依赖关系和上述构建输入判断）；lint、格式检查继续全量跑。

## 5. 兼容性与安全

- 插件发布时必须声明 `api` 范围，宿主只提示安装兼容的版本。
- 宿主 API 有不兼容变化时，先发宿主，再发依赖新 API 的插件。
- npm 发布使用 GitHub Actions 的可信发布（OIDC），不保存长期有效的 token，并附带来源证明（provenance）。npm 要求包先存在才能配置可信发布，所以每个包第一次要用一次性 token 手动发布。
- 待定：宿主安装更新时，是否校验 npm 包的来源证明，确认它确实由本仓库的工作流构建。现在客户端只校验 registry 返回的完整性值。不校验的话，npm 账号一旦被盗，攻击者就能向所有用户推送代码。

## 6. 现有的隐藏耦合

- 翻译、OCR、截图的界面是从宿主源码 `apps/desktop/src/features/*` 导入的，只是运行在通用插件窗口里。
- 每个插件构建时都会引用少量宿主文件（如 `App.css`、`persistence.js`）。
- 便签耦合最深，见第 7 节。

在第 4 节的指纹检查生效之前，这些插件不能只看自己的目录来判断是否需要发布。

## 7. 便签拆分

便签目前的界面在宿主里（`src/features/notes`、`capsules` 等），通过几十个宿主专用 IPC 命令和专门的 `spark233://notes` 来源读写数据。纸片、置顶、贴边胶囊、桌面便签卡片、托盘“找回便签”、提醒、设置、数据目录、备份恢复和停止流程，都是宿主为便签写的专用代码。插件后端还直接导入宿主内部模块（`store.ts`、`reminders.ts`、`security.ts`）。

拆分步骤：

1. **补齐通用能力**（按宿主 API 版本发布）：
   - 窗口：置顶（含全屏检测）、无边框或透明窗口、按文档复用窗口、自定义右键菜单。
   - 浮动或贴边窗口。
   - 由插件提供的桌面卡片。
   - 插件提供的动态托盘子菜单。
   - 定时通知。
   - 插件自己声明的设置项。
   - 通用的“停止前保存”流程。
   - 搜索和 MCP 的扩展点。
2. **搬迁便签**：
   - 界面和数据代码（`NoteStore`、`Reminders`）移进 `packages/official/notes`。
   - 界面改用 SDK，从通用插件窗口加载。
   - 数据存进插件数据区，不迁移旧数据。
3. **清理宿主**：删除 `notes_*` 等命令、`spark233://notes` 来源、命令权限里的 `notes` 标记，以及运行时、备份、托盘、桌面层中的便签专用分支。

## 8. 实施顺序

见 [launcher-todo.md](launcher-todo.md) 的「宿主与插件独立发布」一节。

## 9. 阶段一实现（2026-11-07）

- `scripts/plugin-release.json`：独立发布的插件清单（快捷链接、流量监控、应用搜索）及各自原生组件的源码范围。
- `scripts/build-official-plugins.mjs`：
  - 打包时生成发布用的 `package.json`，并写入指纹 `spark233Build.fingerprint`；
  - `--skip-native` 只用于计算指纹；
  - `--published`（或 `SPARK233_PUBLISHED_PLUGINS=1`）让独立插件按源码版本号从 npm 下载，不再从源码构建；
  - `release.json` 记录每个包的版本、文件和指纹。
- `scripts/plugin-release.mjs`：`plan` 判断哪些插件该发布、哪些内容变了却没升版本；`publish` 构建单个插件，核对指纹后发布。
- `.github/workflows/release.yml`：main 推送时运行，先发布到期的插件，再在宿主版本号没有对应标签时发布安装包。
- `.github/workflows/pulls.yml`：按改动范围执行 typecheck 和测试，并检查插件指纹。
- `build-artifacts.yml` 不再由标签触发，只保留手动构建。

与第 3 节的偏差：没有单独的锁定清单。源码 `package.json` 里的版本号就是内置插件的锁定版本，main 上的版本号总是已经发布或正在发布。

开启前（仓库变量 `SPARK233_NPM_READY` 不是 `true`）：不发布插件，宿主仍从源码构建所有插件，PR 中也没有可比较的已发布版本。
