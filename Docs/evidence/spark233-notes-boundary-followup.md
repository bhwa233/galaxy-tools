# 便签业务边界尚未完成的实现续作

> 2026-10-26：下文描述发现缺口及暂停时的历史输入。真实数据引擎和 main 异步接线已完成当前源码续作，接线过程见[utility 接线记录](spark233-notes-utility-integration.md)，通用备份、崩溃恢复与最新 Windows 候选见[本轮收口](spark233-notes-finalization.md)。

日期：2026-10-25。依据为架构 4.1/4.3 和 TODO P3.1/P3.3，不新增独立于原目标的范围。

已确认源码现状：`packages/official/notes/backend.mjs` 仅校验命令并返回 `action`；`electron/plugins/official/notes.ts` 接收主进程提供的 `newNote/search/open` 回调；`electron/main.ts` 仍创建并直接调用 `NoteStore`，负责正文、分类、附件及便签搜索。便签 renderer 已从插件安装目录加载，资源生命周期、保存拒绝和固定样本证据有效，但这些证据不能证明业务引擎已经随独立包发布。

架构明确要求“宿主不依赖便签路径、词典结构、历史表或 Pulse 索引格式。系统调用桥接可共用，业务引擎与原生程序随所属插件包分发”。当前存储实现仍编进宿主，因此单独更新 notes 包不能更新真实存储引擎。原 P3.1 仅依据固定数据与生命周期而完整勾选的结论不充分，现撤回为部分完成；未删除原成功报告或改写其输入。

后续必须让实际数据引擎由插件包持有，继续使用现有可信 backend utilityProcess、能力和生命周期边界，不在主进程直接执行插件代码，也不以换目录、增加清单字段或增加测试替代抽取。宿主窗口、系统通知和资源编排可以作为受控桥接保留。数据版本、外部 Markdown 目录、备份一致性和更新失败恢复必须延续原合同。

另一个当前源码可触发的启动边界正在复现：主进程在插件启用判定前无条件构造 `NoteStore`，其构造函数调用 `ensure()`；启动还会加载提醒和布局、构造便签托盘数据。便签已经停用时，若仅该插件的目录不可用，宿主仍可能提前失败。这条问题先用 `local-build/` 私有阻塞文件和真实 main 验证，取得结果后再补最小回归与修复。此处尚未宣称动态复现成功。

基于该记录，不能把全部剩余工作归为人工验收。完整一期目标保持未完成；已经通过的 `ui-contract-followup` 产物仍证明其原始字节，后续源码修改需重新构建并绑定新候选。
