# 插件声明配置与启动器解耦方案

日期：2026-10-30

状态：已实施；声明合同、窗口服务、独立 renderer 和插件包构建已落地。验证边界见文末，前一轮确认的窗口布局继续沿用。

## 1. 目标

插件拥有自己的入口、窗口、图标、页面和业务配置。启动器只消费插件注册信息、查询结果和命令激活接口，不决定插件使用哪个页面、窗口有多大或如何查词。

本次任务栏标题、图标调整作为这次声明合同的首个使用场景。不能只增加图标映射表，也不能把原有启动器中的插件分支改写成另一份全局配置表，就宣称完成解耦。

## 2. 迁移前依赖与目标归属

下表记录迁移前的耦合及本次迁移目标；当前实施结果见第 11 节。

| 当前实现                             | 耦合表现                                        | 目标归属                          |
| ------------------------------------ | ----------------------------------------------- | --------------------------------- |
| `shared/launcher-entries.ts`         | 按插件 ID 写主入口、操作、关键词入口和隐藏命令  | 插件各命令的启动器展示声明        |
| `features/plugins/PluginIcon.tsx`    | 按插件 ID 选择 Lucide 组件                      | 插件随包发布的图标声明与资源      |
| `features/launcher/Launcher.tsx`     | 导入并渲染搜索、词典、剪贴板、OCR、截图历史页面 | 插件各自的 renderer 入口          |
| `host/launcher-runtime.ts`           | 按插件工作区类型设置尺寸、窗口标识和带词载荷    | 通用窗口服务与插件窗口声明        |
| `host/desktop-windows.ts`            | 所有窗口使用 `spark233` 标题和应用图标          | 插件窗口配置经宿主解析后的身份    |
| `scripts/build-official-plugins.mjs` | 多个插件复制同一份宿主业务 renderer 构建        | 按插件自身声明构建、装配 renderer |

当前各插件的业务后端、能力代理和保存保护继续承担原有职责；配置迁移不代替业务逻辑迁移。

## 3. 配置的归属

### 3.1 插件公开声明：沿用每个插件的 package.json

公开声明统一放在 `packages/official/<plugin>/package.json` 的 `spark233` 中。继续复用现有 SDK 清单校验、版本、安装完整性和本地化合同，不额外增加一份与 `package.json` 重复的 `plugin.json`。

| 配置内容                                           | 声明位置                       | 消费方                     |
| -------------------------------------------------- | ------------------------------ | -------------------------- |
| 插件 ID、名称、版本兼容、能力与依赖                | 现有 `spark233` 清单字段       | SDK 与插件管理器           |
| 默认图标及 Windows 图标                            | `spark233.ui.icon`             | 启动器、插件市场、窗口服务 |
| 各类窗口的入口、名称、图标覆盖和默认几何参数       | `spark233.ui.windows`          | 通用窗口服务               |
| 命令作为主入口、操作、关键词入口或隐藏项的展示方式 | `spark233.commands[].launcher` | 启动器目录与排序           |
| 命令关联的窗口                                     | `spark233.commands[].window`   | 命令分发与窗口服务         |
| 命令输入类型、匹配、快捷键、托盘与依赖             | 复用现有 commands、tray 等字段 | 现有命令、快捷键、托盘服务 |
| 名称与窗口标题的多语言文案                         | 对应声明的 translations        | SDK 本地化与插件 renderer  |

这里的“默认”是插件初次打开时的默认值；不覆盖用户保存的窗口位置、尺寸和业务偏好。

### 3.2 插件内部静态配置：放在插件目录内

插件页面的导航项、默认页、业务默认值、筛选选项等也归插件所有。简单内容可保留在公开声明中；只供插件内部使用的复杂配置放在插件自己的 `config/` 目录，由插件 renderer/backend 读取。宿主和启动器不解释其业务字段。

例如词典的左侧导航顺序、默认进入哪一页可以由词典自身配置；查词成功后自动展示首个释义属于插件业务代码，不能靠宿主读取一个配置项后代为实现。

内部导航配置引用插件自己的页面 ID；页面 ID 对应哪个组件，由插件自身入口注册，不在启动器里注册组件。

### 3.3 用户运行时配置：仍留在插件私有数据中

暂停剪贴板记录、排除路径、翻译服务设置、历史记录等继续使用现有配置与持久化接口。需要文件化的插件偏好可保存为私有 `settings.json`；已有数据库配置和凭据存储不因本方案强制改写为 JSON。

- 发布包只携带默认值，不携带用户历史、API Key 或运行时状态。
- 插件更新迁移配置，不用新包默认值覆盖用户配置。
- 凭据继续走已有凭据保护方式，不以明文写入插件包或公共配置。
- 配置编辑与保存属于插件配置页，开启、更新和删除仍属于插件市场。

## 4. 窗口配置合同

`ui.windows` 是按窗口用途命名的声明集合，同一插件可以有多个窗口配置。

| 字段                    | 含义                         | 规则                                                             |
| ----------------------- | ---------------------------- | ---------------------------------------------------------------- |
| 窗口配置 ID             | 如 main、quick、result       | 稳定标识，供命令引用，不使用窗口中文标题作为 ID                  |
| entry                   | 插件 renderer 页面入口       | 插件包内相对路径；可复用现有入口，但不能指向启动器页面           |
| title / translations    | 原生标题与可见标题的默认文案 | 未声明时回退到本地化插件 displayName                             |
| icon                    | 当前窗口的图标覆盖           | 默认继承插件图标；PNG 用于界面与原生窗口，ICO 用于 Windows Shell |
| size / minSize          | 初始尺寸与最小尺寸           | 宿主约束到当前显示器可用区域；已有用户几何状态优先               |
| resizable / maximizable | 普通窗口交互能力             | 受宿主支持范围约束；不暴露任意 BrowserWindow 选项                |
| taskbar                 | 是否显示任务栏按钮           | 普通独立窗口可显示；紧凑形态保持原有约定                         |
| reuse                   | singleton 或 document        | 单例按插件及窗口配置复用；文档窗再加入文档 ID                    |
| presentation            | standard 或 compact          | 使用共享窗口外壳的表现方式，不承载查词等业务逻辑                 |

固定由宿主管理的规则不作为可关闭的配置：renderer 就绪后再显示窗口、保存确认、插件停用时的资源回收、调用方验证、权限、sandbox 和 contextIsolation。

### 4.1 同一插件的多个窗口

| 插件       | 窗口配置示例        | 原生标题示例                               |
| ---------- | ------------------- | ------------------------------------------ |
| 文件搜索   | main                | 文件搜索                                   |
| 词典与翻译 | main                | 词典与翻译                                 |
| 剪贴板     | main、quick         | 剪贴板历史、快捷剪贴板                     |
| 便签       | main、notepad、tile | 便签管理、快速记事，以及插件提供的文档标题 |
| OCR        | result              | 取字结果                                   |
| 截图       | history             | 截图历史                                   |

这张表说明各插件应该声明什么，不作为宿主中的另一份按插件 ID 分支表。

动态文档标题由所属插件通过受控窗口 API 更新；不允许通过页面 `<title>` 任意覆盖宿主管理的窗口身份。标题更新不能改变窗口所有者、分组 ID 或图标资源所属插件。

### 4.2 任务栏与图标

1. 窗口创建、复用、重载和切换语言时，按当前已安装版本重新应用标题。
2. 宿主阻止通用 HTML `<title>spark233</title>` 覆盖已经解析的窗口标题。
3. 启动器、插件市场和任务栏使用同一插件声明中的资源，不再维护三个插件图标映射表。
4. Windows 分组身份由宿主根据插件 ID 稳定生成，插件不能自行声明任意 AppUserModelID。窗口图标和 Shell 图标均由宿主设置。
5. 设置、启动器等宿主窗口使用宿主自身声明，不冒充任何插件。进入某插件的配置页不改变设置窗口的所有者。
6. 图标失效时使用通用插件图标并提供诊断；插件缺少可用 renderer 入口时，报告该插件不可用，不进入永久加载状态。

## 5. 启动器入口合同

每个公开命令通过 `launcher` 字段声明展示角色：

| role         | 用途                                                                   |
| ------------ | ---------------------------------------------------------------------- |
| entry        | 插件图标区的主入口；每个插件最多一个，可以没有                         |
| action       | 操作列表中的可执行命令                                                 |
| keyword-only | 输入匹配后才出现的入口                                                 |
| hidden       | 不作为普通搜索候选；通过插件内部界面、托盘或已授权快捷键等既有途径使用 |

`hidden` 只控制展示，不会把 internal 命令变为公开命令，也不构成授权。关键词、输入匹配和命令依赖仍使用现有字段。

命令的 `window` 引用当前插件声明的窗口配置。启动器执行命令时传递现有的激活上下文和请求身份；不构造 `dictionary-input` 等具体插件业务对象，也不直接触发查词或翻译。

词典或搜索插件收到自己的命令和文本后，由自身 renderer/backend 决定如何自动搜索。AI 翻译仍须由明确的翻译动作触发；打开窗口或配置不会自行发起网络请求。

## 6. 声明示例

以下是已支持的文件搜索插件声明节选，完整配置以插件 package.json 为准：

```json
{
  "spark233": {
    "id": "spark233.search",
    "displayName": "文件搜索",
    "ui": {
      "theme": "^1.0.0",
      "icon": {
        "png": "assets/icon.png",
        "ico": "assets/icon.ico"
      },
      "windows": {
        "main": {
          "entry": "renderer/index.html",
          "title": "文件搜索",
          "translations": {
            "en-US": { "title": "File search" }
          },
          "size": { "width": 1040, "height": 700 },
          "minSize": { "width": 640, "height": 420 },
          "resizable": true,
          "maximizable": true,
          "taskbar": true,
          "reuse": "singleton",
          "presentation": "standard"
        }
      }
    },
    "commands": [
      {
        "id": "workspace",
        "title": "文件搜索",
        "window": "main",
        "launcher": { "role": "entry" }
      },
      {
        "id": "open-search",
        "title": "搜索文件",
        "inputs": ["text"],
        "match": "text",
        "window": "main",
        "launcher": { "role": "action" }
      }
    ]
  }
}
```

`workspace` 与 `open-search` 复用同一个窗口配置；前者只打开窗口，后者由插件按收到的文本执行搜索。该行为由插件激活处理器实现，不需要启动器认识这两个命令的业务含义。

## 7. 配置之后还要做的代码解耦

```mermaid
flowchart LR
  Declaration[插件声明和资源] --> Registry[宿主插件注册表]
  Registry --> Launcher[启动器：发现与查询]
  Launcher --> Activation[统一命令激活接口]
  Activation --> Plugin[插件激活处理器]
  Plugin --> Windows[宿主通用窗口服务]
  Registry --> Windows
  Windows --> Renderer[该插件自己的 renderer]
  Renderer --> Bridge[现有受控桌面桥接]
```

- 启动器不再导入或渲染各插件的 Workspace 组件。
- 插件包提供自己的 renderer 入口，使用共享的主题、标题栏、基础组件和生命周期适配。复用共享代码不等于复用启动器作为插件容器。
- 开发模式和生产模式都进入同一个插件入口合同；开发模式仅改变资源服务地址。
- 现有文件搜索、本地词典等页面可以先沿用当前组件，迁移入口和依赖后再按需要移动代码目录；不重做已确认布局。
- 官方插件包按自身入口构建和装配，不能继续仅把完整宿主业务包复制给每个插件，作为最终解耦结果。
- 插件页面读取必要的能力状态，不能为了判断另一个功能是否可用而依赖整个启动器状态对象。
- 窗口接收激活载荷通过通用的窗口激活队列；队列按插件实例、窗口配置和激活 ID 隔离，不复用启动器搜索候选会话。

新增一个使用已有能力的普通插件，不需要给 `Launcher.tsx`、图标映射表或窗口类型 switch 增加分支。新增系统能力仍需扩展宿主代理及权限合同，不能仅用配置开启。

## 8. 校验、回退与兼容

- SDK 定义一个声明 schema，宿主、构建脚本和插件开发都复用它。
- 命令引用的窗口必须存在，入口角色数量和窗口复用策略必须有效。
- 图标和页面只允许插件包内相对路径；复用已有目录边界、符号链接和安装完整性检查，拒绝远程 URL 与越界资源。
- 安装和构建阶段检查所声明资源存在，并限制图片大小、格式和解码结果；打包必须包含声明引用的文件与许可证。
- 缺少新声明的旧插件保持兼容，使用已有 displayName、入口及通用图标；不在新启动器里补回官方插件 ID 表。
- 声明采用新字段的插件需声明匹配的最低宿主版本，避免旧版本严格清单校验拒收。
- 官方插件的旧窗口布局记录做一次明确迁移：保留尺寸、位置与文档归属，将旧工作区标识绑定到新的窗口配置 ID。迁移不删除用户数据。

## 9. 建议实施顺序

| 阶段 | 工作                                                   | 完成标准                                           |
| ---- | ------------------------------------------------------ | -------------------------------------------------- |
| 1    | 确定声明合同及 SDK 校验，补齐官方插件资源和声明        | 配置有唯一来源，旧插件仍可加载，新资源可打包       |
| 2    | 通用窗口服务消费声明，接入原生标题、图标、本地化与复用 | 任务栏显示对应插件，页面加载不会还原为 spark233    |
| 3    | 启动器消费命令展示声明与图标，迁出各插件页面           | 删除原有插件 ID 展示表和 Launcher 内的插件页面分支 |
| 4    | 各插件拥有 renderer 构建入口，迁移激活交接与窗口状态   | 独立窗口不运行启动器查询，关闭插件不影响其他插件   |
| 5    | 按插件验收及安装包验证                                 | 快捷键、托盘、带词打开、保存保护和包内资源均通过   |

阶段 2 只能称为“任务栏身份配置完成”；阶段 3、4 完成后才称为“启动器与插件独立窗口解耦”。

## 10. 验收边界

- 文件搜索带入启动器当前文本并自动搜索；词典按自己的命令查词，不触发 AI 翻译。
- 相同插件窗口复用时收到新激活，不被旧载荷或旧查询覆盖。
- 关闭、停用、更新前继续执行原有保存/取消协议；失败或超时不能自动终止正在运行的业务进程。
- 插件停用或更新时，窗口、快捷键、托盘、资源 URL 和激活队列按所属实例释放。
- 启动器、插件市场和任务栏的图标来自同一插件包；切换语言、页面重载后原生标题保持正确。
- 便签多文档和快捷剪贴板的特殊生命周期单独验证，不强套普通单例窗口。
- 使用新增普通示例插件验证：只声明入口、图标、窗口并提供自己的页面，即可由启动器发现和打开；无需修改启动器源码。
- 自动化与真实 Windows 任务栏验证分别记录，最后核对安装包内的声明、入口和图标文件。仅开发窗口通过不等于发布验收。

布局的逐插件决定继续以 [插件独立窗口布局 PRD](plugin-window-layout-prd.md) 为准；本方案调整配置和代码归属，不重新排列已经确认的功能入口。

## 11. 实施结果与边界

- 宿主 API 升至 1.3；7 个官方插件声明图标和命令展示角色，6 个带页面的插件独立构建 renderer。
- 删除 `shared/launcher-entries.ts`；启动器不再导入插件页面。构建检查禁止插件入口导入 `Launcher.tsx` 或宿主 `App.tsx`。
- 窗口身份、默认尺寸和复用读取插件声明；官方窗口几何状态保存至宿主 `host/plugin-windows.json`，不依赖便签数据库。旧标识通过 `legacyLabels` 迁移。
- 搜索、词典与翻译、剪贴板的静态选项迁至各插件的 `config/ui.json`；历史、凭据和用户偏好保留原存储。
- 激活交接按所属实例及递增修订号隔离；相同关键词重复打开能重新搜索。关闭和停用继续服从保存确认。
- Hello Web 使用相同公开声明，由普通 Web 插件运行时打开，权限仍仅为私有存储。

自动化、构建和 Windows 运行证据见 [实施验证记录](evidence/plugin-declaration-decoupling-2026-10-30.md)。
