# 启动器可用性与插件统一接入方案

日期：2026-11-17。

状态：Q1–Q9 已确认，已按用户要求完成本轮代码实现与本地验证。真实 Windows 证据及剩余验收见第 10 节；不包含发布 SDK 或插件。

## 1. 结论与适用范围

保留现有宿主、启动器、插件管理器、窗口协调器和承载适配器分层。本轮围绕启动器可用性、窗口恢复意图和任务归属补齐一致合同，先调整宿主边界，再贯通截图并接入其余官方插件；具体实现与证据见第 10 节。

本轮范围已确认：

- 检查并调整仓库中的 9 个官方插件：应用搜索、文件搜索、快开、词典与翻译、剪贴板、便签、截图、OCR、流量监控。
- 调整通用 SDK、Web/native 与 uTools 的宿主适配层；复用已有协议、资源作用域和窗口 API，只有现有接口不足时才扩展。
- 外部第三方插件包通过宿主适配接入，不要求批量修改第三方源码。旧插件的降级边界见 Q9。
- 官方可信页面、隔离 Web 页面、原生工具、声明式 HUD、uTools runner 保留各自承载与权限边界。统一的是行为合同和生命周期，不要求所有插件变成同一种页面。

本文不把之前的白屏、截图取消后无法唤起，认定为已经定位到同一个根因；下面的源码事实证明存在需要调整的路径，具体故障仍需分别复现、取证。

## 2. 已确认决定

| 编号 | 决定                                                                   | 约束与例外                                                                                                               |
| ---- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Q1   | 插件启动缓慢、更新、备份或恢复期间，启动器和设置仍可打开               | 显示真实状态，只禁用受影响的命令；关闭、退出始终可用。数据目录不完整时，界面可展示状态，依赖该数据的命令仍不得执行       |
| Q2   | 任务结束后的恢复行为按触发来源决定                                     | 从启动器发起，且没有被用户后来的操作取代时才恢复启动器；全局快捷键发起则恢复原窗口；已展示结果窗或图钉时，不额外弹启动器 |
| Q3   | 全屏截图选区或标注期间，用户主动唤起启动器，会取消本次截图后显示启动器 | 取消不能无限等待，不影响其他原生任务；这是用户新的主动操作，优先于旧任务的恢复意图                                       |
| Q4   | 页面临时任务与插件后台服务分别管理                                     | 页面发起的临时查询、翻译等任务随页面关闭取消；剪贴板监听、流量采集等后台服务继续；任务取消不阻塞关窗                     |
| Q5   | 覆盖全部 9 个官方插件及通用宿主适配层                                  | 外部第三方包保留原实现，经适配接入                                                                                       |
| Q6   | 保留停用、更新、卸载、备份和恢复的数据一致性校验                       | 失败只取消对应管理操作并说明原因，不能拦住宿主界面、用户关窗或退出；不能在不完整的恢复目录上执行业务命令                 |
| Q7   | 本次截图无法正常取消时，可在超时后仅终止本次会话拥有的原生进程         | 必须核对会话、资源所有者及进程身份；不能按进程名批量结束，也不能结束截图插件后台或其他任务                               |
| Q8   | 同一窗口实例有多个展示时，最后一个展示关闭后才取消页面临时任务         | 关闭普通桌面或卡片桌面的一个展示，不影响仍在使用的另一个；后台服务独立运行                                               |
| Q9   | 旧版或第三方插件缺少取消接口时，宿主停止等待并丢弃迟到结果             | 不宣称其内部任务已停止，也不因此终止整个插件后台；官方插件应接入真实取消处理                                             |

此前已经确认的关闭规则继续生效：用户关闭窗口或退出应用，不得被保存失败、超时、未收到插件确认或确认弹窗否决。正常保存独立执行；直接关闭不承诺保住尚未保存的编辑。

本表定义产品行为。实施前发现的问题保留在第 3 节，最终代码及已验证范围见第 10 节。

## 4. 目标职责

| 层                     | 负责                                                                 | 边界                                                     |
| ---------------------- | -------------------------------------------------------------------- | -------------------------------------------------------- |
| 宿主启动与界面引导     | 托盘、快捷键、启动器/设置基础界面、加载及恢复状态                    | 不等待所有插件完成初始化才提供可见反馈                   |
| 启动器呈现             | 用户唤起、隐藏、失焦处理、临时任务让位、来源窗口恢复、展示意图有效性 | 普通界面操作与插件运行状态分离；用户后来的主动操作优先   |
| 启动器查询与执行       | 公开命令目录、上下文匹配、搜索会话、结果排名、执行与进度展示         | 不解释插件页面组件、业务字段或具体原生进程细节           |
| 插件管理器与资源作用域 | 插件身份、启停、权限、后台服务、调用与取消的所有权                   | 一个插件或一次请求的故障不成为无边界的全局锁             |
| 窗口协调器             | 实例/展示身份、打开、复用、恢复、关闭与跨环境展示                    | 区分关闭一个展示和释放整个窗口实例；迟到恢复须可失效     |
| 承载适配器             | 官方页面、Web、native、声明式内容、uTools 的具体协议转换             | 适配承载差异，不自行形成另一套启动器恢复政策             |
| 插件业务               | 自己的页面、数据、业务配置、查询/任务处理及业务结果                  | 通过受控合同请求窗口和报告任务，不直接操作全局启动器状态 |

触发来源与展示意图优先放在宿主内部的调用上下文中。当前 PluginActivation 和窗口旁路上下文各自已有用途；不预设要把可信来源或任意宿主控制字段开放给第三方页面。只有发现插件必须参与的新语义时，才评估 SDK 类型、协议版本及最低宿主版本的扩展。

## 5. 启动与宿主可用性

### 5.1 基础界面

宿主完成必要的本地初始化后即可建立启动器和设置基础界面。插件目录、服务启动和窗口恢复分别报告状态，慢插件显示自己的状态或错误，不拖住整个首屏。

配置尚未返回时提供可见加载状态；读取失败或页面加载失败时提供可理解的错误与重试。不能以永久空窗口作为等待方式。使用缓存配置或安全显示默认值时，应区分临时显示状态与已持久化配置，不能写回覆盖用户配置。

### 5.2 维护状态

维护期间允许展示界面、当前操作状态、诊断及退出入口。能否执行命令，由受影响的数据、插件与事务阶段决定。

配置暂不可编辑或插件数据正在交换时，相应控件禁用并说明原因。恢复失败留下不完整目录时，继续允许查看状态和退出，但禁止启动依赖该目录的业务命令。不能为让界面可打开而取消路径校验、事务日志或回滚保护。

## 6. 展示意图与任务结束

每次主动唤起、临时让位、打开结果、关闭展示或切换任务，都应能判断它属于哪次有效意图。复用已有请求身份、作用域和呈现计数机制，补齐异步边界上的失效判断。

| 场景                                    | 目标行为                                                   |
| --------------------------------------- | ---------------------------------------------------------- |
| 启动器内发起截图，随后取消              | 若原意图仍有效，恢复启动器                                 |
| 全局快捷键发起截图，随后取消            | 恢复截图前窗口，不额外弹启动器                             |
| 截图选区/标注未结束，用户主动唤起启动器 | 取消当前截图，按 Q7 处理超时后显示启动器                   |
| 截图或识别成功并打开结果窗口            | 结果窗口获得展示，不再由旧回调弹出启动器                   |
| 图钉发布成功                            | 保留图钉，不额外弹启动器                                   |
| 用户在等待期间开始了另一项操作          | 原任务的自动恢复意图失效，不能抢回焦点或覆盖新输入         |
| 用户关闭了仍在加载的插件展示            | 旧加载或恢复结果不再显示该展示；以后显式重新打开是新的意图 |
| 来源窗口已不存在或已不适合恢复          | 放弃该次自动焦点恢复；后续手动唤起启动器仍可用             |

任务的业务结束、结果展示和资源清理应分开处理。清理失败要记录并回收其拥有的资源，但不能让启动器永远等在清理 Promise 后面。系统造成的正常焦点转移与用户新的主动操作，需要在实施时依据可信输入和窗口事件区分。

## 7. 取消、关窗与管理操作

### 7.1 截图会话

先请求本次截图会话正常取消，并给它有限的退出时间。超时后，仅对宿主已登记、身份仍匹配的本次会话进程执行终止，再完成启动器唤起。

身份不匹配时不得扩大终止范围；应保留无法安全终止的诊断，启动器仍须进入可见、可操作的状态，不能把无法终止当作继续无限等待的理由。如果原生覆盖层或窗口层级仍挡住启动器，则该场景验收失败，不能只以宿主请求已经返回判定完成。禁止按进程名称扫描后批量结束，也禁止把一个截图会话的失败升级为终止整个截图插件或其他原生任务。

具体合作取消与进程回收时限属于实施参数，结合现有控制协议和 Windows 实测确定；必须有界，不能沿用无期限等待。本文未规定未经实测的响应时间承诺。

### 7.2 页面任务、展示与后台服务

- 任务需要能识别归属：某次查询、某个窗口实例，或插件后台服务。
- 关闭一个展示时先处理该展示；同一实例仍有其他展示时，页面任务继续。
- 最后一个展示被用户关闭时，取消该实例拥有的临时查询/翻译等任务，撤销其迟到结果展示权。最小化、普通失焦不等于关闭展示。
- 窗口为性能保持预热，也不能让已关闭页面的临时任务无限继续。
- 插件后台服务按插件生命周期运行，不能因关闭详情页而停止剪贴板记录或流量采集。
- 已提交的持久化写入与管理事务不当作临时查询一并取消；正常保存继续独立执行，但不能因此阻止关窗。

官方插件应让取消真正到达后台或原生执行方。旧插件没有取消接口时，宿主只能保证停止等待、撤销宿主授权范围内的后续展示并丢弃迟到返回；不能保证旧插件内部已停止计算、网络请求或其他内部副作用。已有信任与能力边界继续约束这些行为。

### 7.3 管理操作

用户关闭/退出与停用、更新、卸载、备份、恢复是不同决策。后五类操作仍按各自要求准备保存、暂停服务及验证数据；失败时取消对应操作并说明原因。

用户仍可关闭窗口或退出应用。退出中断管理事务时，下一次启动依靠现有事务日志和恢复流程识别状态，不能把未完成恢复当作成功，也不能为强行打开业务而跳过一致性校验。

本会话已经修改过关闭与退出路径，不代表所有插件都已完成本节的任务归属和取消改造。已有退出清理时限也不等于截图取消时限。

当前没有阻塞方案的未决产品问题。仍需在实施时查证的工程问题，包括具体取消时限、原生进程退出证据、输入与焦点事件的识别方式、现有合同是否足以承载所需状态，以及 SDK 如需扩展时的版本门槛。这些应通过源码和实验决定；若实验表明必须改变 Q1–Q9 的用户可见行为，再带着具体取舍重新讨论。

后续代码实施顺序：

1. **宿主基础可用性**：拆开首屏与插件初始化依赖，处理配置读取等待、可见加载/错误状态、窗口与调用方 ID 使用。
2. **统一展示意图与竞态**：把隐藏、恢复、结果显示与用户操作优先级交给宿主，补齐关闭后的异步失效检查。
3. **截图贯通验证**：先实现 Q2/Q3/Q7，证明全屏原生流程不会让启动器失去可用性。
4. **官方插件全量接入**：按上一节逐个核查任务归属、真正取消、后台服务和结果窗口，不只修改声明。
5. **通用承载与旧插件兼容**：验证 Web/native/uTools 及旧 SDK 的 Q9 行为，确认权限没有因统一接入而扩大。
6. **文档与验收收口**：同步所有相关合同，记录自动化、真实 Windows、构建和打包各自证据。

按用户授权执行上述顺序。既有未提交改动继续保留，不以本方案为由重置工作区。

### 10.1 本轮实现

- 宿主协议和 IPC 安装后即预加载启动器、建立托盘及宿主快捷键；二次启动的显示请求不等待插件和卡片恢复。配置读取退出全局事务队列，React 挂载不等待配置；读取超时可重试，页面异常有独立关闭入口，不写回临时默认配置。
- `HostLifecycle.shellBlocked` 与业务维护状态分开；维护期间设置/启动器可打开，设置控件显示原因并禁用。恢复失败进入维护状态，不启动未恢复的数据服务。插件完成元数据恢复后，已就绪插件可在其他启动服务仍等待时执行。
- 宿主集中持有截图的临时让位与恢复意图；插件报告业务完成，恢复不等待缓存清理。新的唤起、执行、设置和关闭操作使旧恢复意图失效。Windows 焦点观察复用已有取词辅助进程，观察不覆盖来源窗口的恢复身份。
- 截图先合作取消，默认等待 750 ms；超时只回收当前会话子作用域登记的进程，原生进程回收另有 1 s 退出预算。失败记录原因，宿主继续显示。退出回收也覆盖截图/OCR 的子作用域进程，管理操作的保存准备保持独立。
- 窗口打开在排队、恢复和激活边界检查有效性；关闭立即撤销展示，防止迟到重显。临时页面任务按可信窗口实例归属，最后一个展示关闭才取消；便签已接受写入与后台服务保持独立，来源实例关闭后不再打开迟到结果窗。
- 管理器激活接收宿主取消信号，通用 Web/native、官方适配和 uTools 贯通取消或停止等待。Web 页能力请求随页面释放取消；旧插件只保证宿主不等待及拒收迟到展示，不宣称内部副作用已停止。快开补齐统一窗口实例承载，uTools 关闭一处共享展示不隐藏仍在使用的另一个。
- 复用已有 SDK 的查询信号、后端激活上下文、窗口定义和资源作用域；本轮没有新增公开激活字段、依赖或 SDK 版本门槛。

### 10.3 验证边界

仍需人工覆盖全屏截图的 Esc、右键、选区/标注与图钉操作，以及多屏、快速跨应用切换后的焦点行为。当前桌面自动化不能选中截图覆盖层，不能用合作取消记录替代这些物理操作。强制终止已做会话隔离回归及真实 Windows 受控卡死替身验证，实际截图会话均合作退出；真实截图覆盖层卡死仍待验。

没有执行安装包安装/升级、注销重启、真实远程翻译提供方或外部第三方包全量验证。第三方兼容通过仓库的 Web/native/uTools 边界回归及本地代表包验证，不扩大既有权限。当前不将 A1–A14 宣称为所有环境全部验收完成。
