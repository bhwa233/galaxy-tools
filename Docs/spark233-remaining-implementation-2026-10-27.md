## 2. 本轮集中代码包

2.1–2.4 是首批复核确认的代码缺口；2.5–2.7 是后续只读复核发现的续修。每批均先写清需求、再集中补齐及统一功能验证；这些补修不代表原清单其余任务已完成。

### 2.1 普通文档类型规则（P5.12）

以正清单替代有限脚本后缀黑名单，宿主与独立应用插件各自执行相同规则，实际启动再次复核。目录只授权目录本身，不枚举或授权其子树。

支持的文档扩展名如下，不区分大小写：

| 类型                           | 扩展名                                                       |
| ------------------------------ | ------------------------------------------------------------ |
| 文本、Markdown、数据或配置文本 | `txt md markdown rst csv tsv log json yaml yml toml ini xml` |
| Office 与开放文档              | `doc docx odt rtf xls xlsx ods ppt pptx odp`                 |
| PDF                            | `pdf`                                                        |
| 常用图片                       | `png jpg jpeg gif webp bmp tif tiff ico heic avif`           |

未列出的扩展名没有普通文档入口权限。`.exe` 保留程序的 argv/cwd 语义，`.lnk/.url` 保留原快捷方式语义；文档和目录不接受 argv/cwd。这是入口类型规则，不承诺分析文档内容或替代系统默认应用的行为。

用户后续明确无需旧配置兼容。本轮不保留旧未知 document 项的特殊读取、改名或同 ID/kind/path 豁免；配置读取与写入统一按当前正清单校验，不符合规则时明确报错，不自动迁移成程序或执行。新建或改变目标仍须宿主选择器/拖放授权；不支持的目标不得进入可执行搜索结果，现有固定目标按不可用处理。

应用插件版本为 1.1.2，数据格式版本保持 1；旧插件的文档描述符也须经过宿主的正清单执行检查。

### 2.2 来源程序进入匹配与实际派发（P3.17）

SDK 0.3 / Host API 1.2 增加以下合同：

- 命令可声明 `sourceApplications: ["winword.exe", "excel.exe"]`，为 1–32 个程序 basename，trim、小写并去重；拒绝路径、控制字符、通配符和 Windows 非法文件名字符。
- `PluginContext` 增加 `{ kind: "window", sourceApplication: "winword.exe" }`；已有 text/image/files 可带可选 `sourceApplication`。
- `inputs`、`match` 支持 `window`。新特性插件声明 `api: "^1.2.0"`，旧插件按原兼容范围继续运行。共享 UI 包保持 0.2.0，SDK 兼容范围扩到 `>=0.2.0 <0.4.0`。

来源由宿主根据原生捕获的来源窗口提供，只包含程序 basename，不传窗口标题、完整可执行路径、PID 或 HWND。renderer、插件参数和原始能力调用自报的来源不构成授权。

没有选区内容但来源仍可信时，可以生成 window 上下文，展示对应程序动作，同时保留常用及固定入口。内容受保护、过大或无法复制不等于允许读取内容；来源已变化、捕获取消或无法确认来源时，不沿用上次的程序身份。

已有文字、图片或文件选区时，按来源程序限定的内容动作仍可匹配。仅接受 window 的动作只接收从受信来源派生的 window 元数据，不额外收到选区正文或资源。

规则必须覆盖普通结果、别名、固定、模式入口、provider 主动作和次级动作。实际派发在冷启动前后重新检查声明和当前来源代次；同一 exe 的新捕获也不能使旧动作重新有效。已经进入业务执行的保存按既有保存规则完成，结果展示独立校验代次。

旧命令未采用新特性时，转发保持原上下文形状：移除新增来源字段，window-only 上下文不强塞给旧插件。缺少宿主受信来源的直接 `commands.invoke` 或 `native.process` 调用不能绕过来源限定；不增加任意 shell 执行权限。

### 2.3 恢复与回滚同步宿主管理状态（P6.14、P2.9）

恢复磁盘后，DesktopPluginHost 的 pending previews、更新结果、检查时间及任务缓存必须与恢复后的状态一致。不能只替换 Manager 快照，而让宿主继续保留恢复前的 pending B，并在下一次保存时覆盖恢复出的 A。

由 DesktopPluginHost 自己提供 `reloadAfterRestore()`，仅在维护屏障已暂停并排空操作时调用。先完整解析恢复后的管理文件，再替换内存；清除易失的旧下载任务、更新缓存和迟到回写能力，恢复持久化检查时间。事务未完成时拒绝覆盖。

Main 在恢复后的 Manager 快照已替换、业务运行实例重新启动前调用该接口；失败回滚也读取回滚后的磁盘状态。不得调用完整 initialize/installBundled 去覆盖用户已恢复的版本、启停或卸载选择。

### 2.4 备份预览令牌属于创建它的文档（P6.14）

保持现有 manifest 指纹绑定，并补齐调用方、生命周期与重选撤销：

- selectionId 只由宿主生成，绑定创建它的 caller/文档身份；另一管理窗口不能恢复或撤销该选择。
- 新一次选择开始就撤销该 caller 的旧选择。选择取消、验证失败、取消确认卡或关闭对话框后，旧令牌也必须在宿主失效。
- 窗口关闭、主 frame 导航或 renderer 崩溃撤销该文档令牌。异步 picker/inspect 的迟到结果不得重新登记到已退休文档。
- 释放请求只针对原 selectionId，迟到的释放不能删除新选择。令牌继续保留十分钟上限。
- 同一令牌的重复恢复请求须拒绝并发执行。保存拒绝等可恢复失败允许在原文档重试；已经接受的恢复事务遵循保存、切换、回滚与数据保护规则，不能强杀冒充取消。

界面提供显式释放接线，宿主重新校验才是最终边界；仅隐藏确认卡不算撤销权限。

为使并发和权限边界直接进入现有 Vitest，Main 中的令牌、检查代次和恢复占用逻辑提取到专用 `BackupSelections`，Main 保留 IPC 参数校验、真实文档身份及窗口存活检查，调用该唯一令牌管理实例。提取不引入新的传输或权限来源；测试直接使用生产状态机，验证重选、退休、精确释放、并发恢复与失败重试。

### 2.5 翻译默认方向（P6.6，续审补修）

原实现只要包含 Han 字符就将原文当作中文，日语“日本語を勉強しています”因此误选英文，与非中文默认译为简体中文的要求冲突。将默认方向规则集中到翻译插件的纯语言策略模块，由后台和前端共同调用，避免维护两份判断。

含平假名、片假名或韩文音节的内容不因同时存在汉字而被当作中文；其默认目标为简体中文。其余含汉字的内容默认译英文，其他内容默认译简体中文。纯汉字短语与中日混合内容仍存在语言歧义，保留用户手动指定目标，不声称该本地规则是完整语言识别器；不为呼出或语言判断新增网络请求或依赖。显式目标语言优先，缓存继续按实际目标区分。通过真实 translator 的请求目标和缓存行为验证，不做 UI 测试。

### 2.6 原生入口初始化失败后的恢复（P2.5、P2.9，续审补修）

首次原生握手失败且从未接受业务执行时，宿主按既有启动失败策略停止该自有进程。确认进程已退出后，移除失败的 entry 和初始化 Promise，使同一插件的其他运行域仍可使用、用户可重试原生入口，停用/卸载不再把该死进程视作未保存业务。只有确认退出的未初始化 entry 可以这样清理；未确认退出的进程仍须跟踪，已初始化后异常退出仍走原崩溃与保存策略，不强杀冒充正常保存。

### 2.7 退出部分释放失败后的恢复（P2.5、P2.9，续审补修）

退出先准备全部实例，再逐个释放。若中途某实例释放失败，保留失败及其未释放资源的真实状态；对尚未释放的其他已准备实例取消停止，使其重新接受命令，并恢复本次退出前已成功释放且仍启用的启动型实例。恢复失败必须明确报告，不能将释放失败当作成功退出。继续复用 Manager 已有的恢复与资源作用域机制，不新增退出协调框架。以三个真实 Manager 资源作用域的功能用例覆盖“前一实例已释放、中间拒绝释放、后一实例仍准备中”的交错。

### 2.8 活动截图恢复 OCR 能力（P4.8、P4.18，续审补修）

截图在 OCR 停用时启动，宿主原先传入固定的 `--spark233-ocr-enabled=false`。之后启用 OCR 虽移除了会话的 `ocr.disabled`，原生端仍被启动参数锁死，不能恢复同一选区取字。

宿主会话改为只通过现有 `ocr.disabled` 文件传达可变化的 OCR 能力，不再传入不可更新的 false 开关。文件初值必须在原生启动前写好，活动期间继续同步启停；最终识别派发仍复核插件可用性。复用现有原生端默认参数语义，不修改原生程序、独立运行行为或增加 IPC。功能用例直接验证真实 CaptureController 的初始会话状态、启用后解除禁用、再次停用及最终派发拒绝，不做按钮或遮罩 UI 测试。

### 2.9 便签正文与索引提交失败（P3.1、P6.14，续审补修）

便签正文写入成功后，metadata 提交若失败，原实现仍留下新正文：同路径更新造成新正文与旧索引不一致，改标题或分类会产生同 ID 的第二个 Markdown，使之后的索引重建失败。

保存须保留目标文件写入前的状态，并在 metadata 提交抛错时恢复原目标内容或移除本次新建的目标。旧正文路径、旧索引与原 ID 保持可读；不留下重复正文，解除故障后可重试、可重建。回滚本身失败须同时报告原错误与回滚错误，不伪报保存成功。此处修复同步提交失败，不据此宣称真实断电下的多文件原子事务已验收，也不新增日志格式或迁移旧配置。最低层 NoteStore 功能用例只注入 metadata 提交失败，实际正文/索引读写及重建使用真实临时文件。便签插件 patch 版本随内置引擎更新。

3. **统一验证阶段**：代码包完成并核对需求覆盖后，针对同一组生产输入进行下节验证。本轮只运行功能用例及常规构建，不生成 Windows 候选。
